# Project Structure

All backend projects live in `backend/`, share `backend/CCC.sln`, and inherit `net10.0`, `Nullable` and `ImplicitUsings` from `backend/Directory.Build.props`. Package versions live only in `backend/Directory.Packages.props` (Central Package Management), so a `PackageReference` names the package without a version. Project names have no `CCC.` prefix, but each sets `RootNamespace`, so namespaces keep it: the `Domain` project's code lives in `CCC.Domain.*`. Projects in a folder add the folder to their namespace, such as `CCC.Modules.TranslationEditor` and `CCC.Base.Dcb`.

The rules for how these projects may reference each other are in [dependency-rules.md](dependency-rules.md).

When these docs say *projection*, they mean a read model: the tables built from the event log to answer queries, together with the `IProjection` that builds them. An *automation* is an `IAutomation` that reacts to events by issuing commands (ADR-014).

- `Api` — ASP.NET Core app. Endpoints, request DTOs, request → value object mapping, `CommandResult` → HTTP mapping, startup (`Program.cs`)
  - Every error is RFC 9457 `application/problem+json` with the message in `detail`: endpoints return `TypedResults.Problem(...)`, and `AddProblemDetails`, `UseExceptionHandler` and `UseStatusCodePages` cover binding failures, unknown routes and unhandled exceptions
  - Endpoints return `TypedResults` with a declared type, so the OpenAPI document shows every status and body. Command endpoints return `CommandHttpResult` from `ToHttpResult()`, which declares 200, 400, 404 and 409 itself. A query declares `Results<Ok<TenantDetails>, ProblemHttpResult>` and lists its problems with `.ProducesProblem(…)`, since `ProblemHttpResult` adds no metadata, including the 400 from `InvalidValueFilter` when it parses route values into value objects. Each `Map<Module>()` maps into a group tagged with the module's name
  - `/health` lists the health check of every projection and automation as JSON and answers 503 if any is unhealthy. A projection is unhealthy while its schema isn't installed, when another version is installed, or when it is stalled, with the stall reason. It is degraded while events are left to apply, such as during a rebuild. An automation reports the same way, without a version
- `Base/` (solution folder `Base`) — the projects every module builds on, other than `Domain` and `EventStore` (ADR-013). Their namespaces follow the folder: `CCC.Base.<Project>`
  - `Abstractions` — the contracts every module shares at its boundary to `Api`: `ICommandHandler<TCommand>`, `IQueryHandler<TQuery, TResult>`, `CommandResult` and `CommandError`. References no other project, and holds nothing else
  - `Dcb` — the building blocks of dynamic consistency boundaries, without any storage (ADR-012): `StateModel<T>`, `IStateModel` (which the loader feeds with `Load(records)`), `StateModelExtensions` (`IsTrue()`, `IsFalse()`, `IsNull(out value)`, `List()`), `EventFilter`, `EventRecord` with `PayloadAs`, `EventHandlers<T>` (the dispatch by event type that state models and projections share) and `Tags`. References nothing
  - `Projections` — the infrastructure every module with projections shares (ADR-011), not the projections themselves, which live in the modules. The `CCC.Base.Projections` namespace marks it as infrastructure: `IProjection`, `ProjectionRunner<T>`, `ProjectionRetryPolicy`, `EventLogRunner` (the base class of both the projection and the automation runner, which follows the event log from a bookmark and retries, stalls and wakes up after appends), `ProjectionDatabase`, `ProjectionHealthCheck<T>`, the Dapper helper `CommandDefinitionExtensions.With`, and the `AddProjectionDatabase` and `AddProjection<T>` registrations. `AddProjection<T>` also registers the projection's health check, named after its schema
  - `Automations` — the infrastructure for automations (ADR-014), not the automations themselves, which live in the modules: `IAutomation`, the `Reaction` delegate, `AutomationRunner<T>`, `AutomationHealthCheck<T>` and the `AddAutomation<T>` registration. Automations keep their bookmarks in the projection database, and their runner derives from `EventLogRunner` in `Projections`, so they share the projections' retry policy and stall handling
  - `TestKit` — what every module test project shares: `InMemoryEventStore`, `CommandFixture` with its `Given…` setup helpers, and `CommandAssert` for handler tests and queries replayed from state models, `ProjectionFixture` for projections and the queries that read them, and `AutomationFixture` for automations. The command fixture registers every module, so tests set up state through other modules' commands and get the same events and tags as production. The projection fixture appends events directly, because projections don't depend on tags. The automation fixture runs against PostgreSQL like the projection fixture, but sets up state through commands, because the commands an automation issues depend on tags
- `Modules/` (solution folder `Modules`) — one project per module, each covering one area of work (ADR-009): `AppAdministration`, `TenantAdministration`, `TeamAdministration`, `TranslationEditor` and `TranslationDelivery`. A module holds the commands, command handlers, projections and query handlers of its area of work, and registers its handlers in an `Add<Module>()` extension. A use case goes into the module whose tasks it changes together with and whose queries it needs; who usually performs it is only a hint
  - Command handlers load state, run the business checks, and append events or return a `CommandResult` error
  - Queries that list things, such as keys, projects or tenants, read from a projection. Queries for the details of a single entity, such as one tenant's name, load a state model through `StateLoader` and need no table
  - A module with projections owns one PostgreSQL schema named after it (`translation_delivery`) and its `IProjection`s. `ProjectionRunner<T>` keeps each projection up to date in the background, woken by `PostgresEventStore` after every append. Raise a projection's `Version` whenever its tables or its logic change, so the module's schema is rebuilt from the first event
  - An automation reacts to events by issuing a command of its own module through `ICommandHandler<T>`, never by appending events itself. Its `Handlers` register one `Reaction` per event type (`.On<TenantRegistered>(e => cancellationToken => addDefaultTeam.HandleAsync(…))`). `AutomationRunner<T>` moves its bookmark after each reaction, so after a crash it reacts to the same event again: the command has to treat that as already done and succeed without appending, as `AddDefaultTeam` does for a tenant that already has a team. A command error stalls the automation like a failing projection. An automation has no version and is never rebuilt
  - A projection turns each event into exactly one Dapper `CommandDefinition`, built by a method named after the event (`AddProject(ProjectAdded e)`) without a transaction or cancellation token. Its `Handlers` register these methods per event type (`.On<ProjectAdded>(AddProject)`), which also decides which events the runner reads. `InstallAsync` and `ApplyAsync` execute them with `.With(transaction, cancellationToken)`. When an event needs a value from the projection, such as the reference language, the SQL looks it up itself
- Inside a module, and inside its folder in `Api`, commands live in `Commands/` and queries in `Queries/`, with the namespaces following the folders (`CCC.Modules.TranslationEditor.Commands`). Projections belong to `Queries/`, since they only exist to serve queries, and automations belong to `Commands/`, since they only exist to issue commands. `ServiceCollectionExtensions` stays at the module root
- One file per use case in `Api` and in the module, named after the command or query: `Api/TranslationEditor/Commands/AddKey.cs` holds `AddKeyEndpoint` with its nested `AddKeyRequest` and a `MapAddKey` extension, `Modules/TranslationEditor/Commands/AddKey.cs` holds the `AddKey` record and `AddKeyHandler`. Each module's folder in `Api` has a `Map<Module>()` extension in `EndpointRouteBuilderExtensions` that maps its endpoints explicitly, and `Program.cs` calls every `Add<Module>()` and every `Map<Module>()`
- `Domain` — the shared kernel every module builds on: domain events (`Events/`), state model definitions and the tag vocabulary (`State/`), value objects (`Types/`). References only `Dcb`
  - State models are grouped into one static class per domain concept, named after it: `Tenant.NameTaken(...)`, `User.EmailTaken(...)`, `Subscription.Exists(...)`. A state model goes into the class of the thing it is keyed by, e.g. `Team.KeysAdded(teamId)`
  - A state model answers a question with a `bool` (`Tenant.IsNamed(tenantId, name)`, `Key.HasTranslation(...)`) or returns a domain type (`Team.Subscription` → `SubscriptionModelId?`). Comparisons belong in a state model, not in the handler. The one exception is the key limit, which spans two loads, so `KeyCount >= KeyLimit` stays in `AddKeyHandler`
  - Reducers turn stored values into domain types with the regular `From`. All stored events are assumed to have passed today's validation, so there is no separate unvalidated path
  - Handlers keep each state model in a variable named after its answer, load them all in one call, and check them afterwards with `IsTrue()`, `IsFalse()`, `IsNull(out var value)` or `List()`, reading `.Value` only where none of these fits: `var idTaken = User.Exists(...); var emailTaken = User.EmailTaken(...); var context = await loader.LoadAsync([idTaken, emailTaken], cancellationToken); if (idTaken.IsTrue()) ...`. Reading `Value` before the model has been loaded throws, so a model left out of the list fails loudly instead of answering with its initial state
  - Endpoints take the request's `CancellationToken` and handlers pass it on to every load, append and query
- `EventStore` — `IEventStore` and its PostgreSQL/Dapper implementation, `StateLoader`, `StateContext.TryAppendAsync` (the conditional append), schema setup, and `AppendSignal`, which wakes the projection runners after every append
  - Each database has one `NpgsqlDataSource`, owned by a singleton that hands out connections: `EventStoreDatabase` for the event log, `ProjectionDatabase` for the projections. Neither the event store nor the projections create an `NpgsqlConnection` from a connection string
  - Dapper's type handlers for `string[]` and `DateTimeOffset` are process-wide. `DapperTypeHandlers.Register()` installs them, and both database types call it from their static constructors, so they are in place before the first query on either database
  - The schema also has an `event_view` view with one row per event and tag, which splits each tag into `tag_key` and `tag_value`, for reading the log by tag in SQL. Events without tags don't appear in it. The view can't use the GIN index on `events.tags`, so the event store's own queries filter `events` directly with `tags @> …`
- `Modules/<Module>.Tests` — a module's tests. Handler tests run against the in-memory `IEventStore` from `TestKit`; projection and query tests run against a throwaway database on the PostgreSQL server in `CCC_TEST_POSTGRES` (defaults to the local development server)
- `Domain.Tests` — value object and state model tests
- `Architecture.Tests` — checks the rules in [dependency-rules.md](dependency-rules.md)
- `Api/Api.http` — smoke test with one request per endpoint and error path, including the expected status and body
